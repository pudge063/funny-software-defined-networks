## Lab 1. Запуск модельной сети SDN

**Суть.** Научиться разворачивать модельную сеть SDN в эмуляторе Mininet,
запускать контроллер и подключать к нему виртуальные коммутаторы.

**Что сделано.**

- Подготовлена ВМ, установлен Mininet 2.3.0 из исходников (`util/install.sh -a`).
- Собран Floodlight v1.2. Для сборки на Ubuntu 22.04 понадобилось:
  - собрать Thrift 0.9.3;
  - заменить `libthrift` и перегенерировать Java-файлы Thrift;
  - поправить импорт `TFramedTransport` и один тест;
  - собрать проект под Java 8.

  Порядок установки описан в [README](./README.md).
- Запущены простейшая сеть `sudo mn` (h1, h2, s1) и линейная топология
  `--topo linear,4 --switch ovsk`, проверены `pingall` и `h1 ping h3`.
- Запущен Floodlight (`java -jar target/floodlight.jar`), сеть подключена к нему
  через `--controller=remote,ip=...,port=6653`.

**Результаты.** `pingall` проходит без потерь. 4 коммутатора проходят handshake
с контроллером (роль MASTER), в веб-интерфейсе Floodlight (`:8080/ui`) на
странице Topology видны 4 коммутатора и 4 хоста.

**Саммари.** Стенд для всех следующих работ готов: эмулятор сети и внешний
SDN-контроллер, который управляет коммутаторами по OpenFlow.

## Lab 2. Анализ пакетов OpenFlow

**Суть.** Перехватить и проанализировать трафик между OpenFlow-коммутаторами и
контроллером.

**Что сделано.**

- Запущен захват `tshark -i any -f "tcp port 6653"`.
- Поднята сеть `linear,4` с `protocols=OpenFlow13`, подключённая к Floodlight,
  выполнены `pingall` / `h1 ping h4`.
- Трафик отфильтрован по `openflow_v4` и разобран.

**Результаты.**

- OpenFlow работает поверх TCP, порт **6653**, версия протокола **OpenFlow 1.3**.
- Наблюдаемые сообщения:
  - `OFPT_ECHO_REQUEST/REPLY` – keep-alive;
  - `OFPT_PACKET_IN` – пакет без подходящего правила отправляется контроллеру;
  - `OFPT_FLOW_MOD` – контроллер устанавливает правило в таблицу потоков;
  - `OFPT_PACKET_OUT` – контроллер указывает, что сделать с конкретным пакетом.
- В `PACKET_OUT` используется действие `OFPAT_OUTPUT`: отправить пакет в
  указанный порт коммутатора.

**Саммари.** Реактивная схема работы SDN: первый пакет нового потока уходит на
контроллер (`PACKET_IN`). Контроллер отвечает `PACKET_OUT` и устанавливает
правила (`FLOW_MOD`) на коммутаторы пути, после чего трафик потока идёт без
участия контроллера.

## Lab 3. Создание правил обработки потока на контроллере SDN

**Суть.** Научиться управлять потоками трафика с помощью контроллера: создать
правило ACL и оценить его влияние на связность и на обмен OpenFlow.

**Что сделано.**

- Запущены захват tshark, Floodlight и сеть `linear,4` (OpenFlow 1.3), выполнен
  `pingall`.
- В веб-интерфейсе Floodlight (Access Control Lists -> Add New) создано правило:
  ICMP, 10.0.0.1/32 -> 10.0.0.4/32, DENY.
- Повторно выполнены `pingall` и `h1 ping h4`. Изучены таблица потоков s1
  (`ovs-ofctl dump-flows`) и захват трафика.

**Результаты.**

- До правила – `0% dropped (12/12)`, после – `16% dropped (10/12)`: недоступны
  h1 -> h4 и h4 -> h1 (эхо-ответ h1 -> h4 попадает под то же правило),
  остальные пары работают.
- При создании правила контроллер проактивно, без `PACKET_IN`, отправил на s1
  один `OFPT_FLOW_MOD`:
  - priority 30000, без таймаутов;
  - match `icmp, nw_src=10.0.0.1, nw_dst=10.0.0.4`;
  - без действий (`actions=drop`).
- Для потока 10.0.0.1 -> 10.0.0.4 обмен с контроллером прекратился. До правила
  на него приходились 1 `PACKET_IN`, 1 `PACKET_OUT` и 4 `FLOW_MOD`, после –
  ни одного сообщения: пакеты отбрасываются на s1. Для остальных потоков обмен
  не изменился.

**Саммари.** Контроллер SDN централизованно задаёт политику доступа и сам
устанавливает её в сеть в виде правил с высоким приоритетом. Заблокированный
трафик отбрасывается на первом коммутаторе и не нагружает контроллер.

## Lab 4. Создание топологий в Mininet

**Суть.** Научиться описывать собственные топологии через Mininet Python API,
задавать параметры каналов (пропускная способность, задержка, потери, очередь)
и проверять их с помощью `ping` и `iperf`.

**Что сделано.** Написаны скрипты на Python 3
([reports/lab4/topologies](./reports/lab4/topologies)):

- `LinearTopo.py` – линейная топология из методички;
- `LinearTopoPerf.py` – она же с `CPULimitedHost` и `TCLink`
  (10 Мбит/с, 5 мс, 1% потерь);
- `TreeTopo.py` (задание 1) – дерево core / aggregation / edge / host с
  настраиваемым fanout `k` и своими параметрами каналов на каждом уровне;
- `RingTopo.py` (задание 2) – кольцо из `n` коммутаторов с `k` хостами на
  каждом. `bw` и `delay` задаются отдельно для звеньев кольца и звеньев хостов.
  Петля обслуживается контроллером Floodlight либо STP (`--stp`).

**Результаты.**

- Линейная топология: `0% dropped (12/12)`.
- С потерями 1% на звено: один пинг из 12 потерян, TCP h1-h4 даёт 1.6 Мбит/с
  вместо 10 из-за потерь на 4 звеньях пути.
- Дерево:
  - k=2: 7 коммутаторов, 8 хостов;
  - k=3: 13 коммутаторов, 27 хостов;
  - 0% потерь в обоих случаях;
  - RTT между крайними хостами 32.8 мс (расчётные 2 x 16 = 32 мс), iperf
    9.5 Мбит/с (узкое место – звено хоста 10 Мбит/с).
- Кольцо 3 x 3: 0% потерь.
  - Звенья кольца 20 Мбит/с / 10 мс: RTT h1-h4 24.3 мс (расчётные 24),
    iperf 9.5 Мбит/с.
  - Звенья кольца 5 Мбит/с / 20 мс: RTT 44.3 мс (расчётные 44), iperf
    4.8 Мбит/с.
- Кольцо 4 x 2 в режиме STP: 0% потерь.

**Саммари.** Mininet API позволяет описывать произвольные параметризованные
топологии, а `TCLink` точно эмулирует характеристики каналов: измеренные
задержки и пропускная способность совпадают с заданными. Топологии с петлями
(кольцо) требуют контроллера, который их учитывает, или STP, иначе возникает
широковещательный шторм.
