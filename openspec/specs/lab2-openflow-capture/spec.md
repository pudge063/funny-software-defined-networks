# lab2-openflow-capture Specification

## Purpose

Лабораторная работа 2 «Анализ пакетов OpenFlow»: перехват и разбор обмена
OpenFlow 1.3 между OVS-коммутаторами Mininet и контроллером Floodlight.

Артефакты:

- отчёт: `reports/lab2/report.md` (команды, вывод `tshark`, ответы на
  контрольные вопросы), скриншот `images/image1.png`;
- сводка: `SUMMARY.md`, раздел Lab 2.

Файл захвата (`/tmp/openflow_capture_v13.pcap`) в репозиторий не входит и
воспроизводится по сценариям ниже. Общие требования к стенду –
`specs/sdn-lab-environment`.

## Requirements

### Requirement: Процедура захвата

Захват SHALL выполняться на интерфейсе `any` с BPF-фильтром `tcp port 6653`
до подключения сети к контроллеру, чтобы в захват попал handshake.
Сеть MUST запускаться командой:

```
sudo mn --topo linear,4 --switch ovsk,protocols=OpenFlow13 --ipbase=10.0.0.0/8 --controller=remote,ip=127.0.0.1,port=6653
```

#### Scenario: Захват и фильтрация

- **WHEN** выполнены
  `tshark -i any -f "tcp port 6653" -w /tmp/openflow_capture_v13.pcap`,
  запуск Floodlight, запуск сети и `mininet> pingall` / `h1 ping h4`
- **THEN** `sudo tshark -r /tmp/openflow_capture_v13.pcap -Y "openflow_v4"`
  выводит сообщения с протоколом `OpenFlow`, адреса `127.0.0.1 → 127.0.0.1`

### Requirement: Транспорт и версия протокола

Обмен между коммутатором и контроллером SHALL идти по TCP на порт контроллера
**6653** и использовать **OpenFlow 1.3** (`Version: 1.3 (0x04)`, диссектор
`openflow_v4`).

#### Scenario: Ответ на контрольные вопросы 1–2

- **WHEN** агент отвечает, какой порт и какая версия OpenFlow используются
- **THEN** ответ – TCP 6653 и OpenFlow 1.3

### Requirement: Наблюдаемые типы сообщений

В захвате SHALL присутствовать сообщения из таблицы R1 (раздел Reference),
и они MUST интерпретироваться согласно ей. Сообщения handshake (`HELLO`,
`FEATURES_REQUEST/REPLY`, `MULTIPART`, `ROLE_REQUEST`) MAY присутствовать,
если захват начат до подключения сети.

#### Scenario: Первый ping между хостами

- **WHEN** хост отправляет первый пакет нового потока
- **THEN** в захвате идёт `OFPT_PACKET_IN` от пограничного коммутатора
- **AND** затем `OFPT_FLOW_MOD` на коммутаторы пути и `OFPT_PACKET_OUT`
- **AND** последующие пакеты потока не порождают `PACKET_IN`, пока правило
  не истечёт (idle-timeout модуля Forwarding – 5 с)

### Requirement: Действие в OFPT_PACKET_OUT

Для потока данных `OFPT_PACKET_OUT` SHALL содержать действие `OFPAT_OUTPUT`
с номером выходного порта коммутатора. Конкретный порт MUST определяться по
детальному разбору (`tshark -V` или Wireshark GUI), а не по однострочному
выводу.

#### Scenario: Ответ на контрольный вопрос 4

- **WHEN** агент отвечает, какое действие указано в `OFPT_PACKET_OUT`
- **THEN** ответ – `OFPAT_OUTPUT` (переслать пакет в указанный порт)
- **AND** для LLDP-кадров контроллера `in_port=CONTROLLER`

### Requirement: Интерпретация реактивной модели

Отчёт и любые выводы по лабе SHALL описывать реактивную схему SDN: первый
пакет потока поднимается на контроллер, контроллер устанавливает правила, и
дальнейший трафик потока обрабатывается в плоскости данных без участия
контроллера.

#### Scenario: Сводка по лабе

- **WHEN** обновляется раздел Lab 2 в `SUMMARY.md`
- **THEN** он содержит порт 6653, версию OpenFlow 1.3, перечень сообщений и
  описание реактивной схемы

## Reference

### R1. Типы сообщений OpenFlow

| Сообщение                      | Направление             | Назначение                                          |
| ------------------------------ | ----------------------- | --------------------------------------------------- |
| `OFPT_ECHO_REQUEST` / `_REPLY` | обе стороны             | keep-alive соединения, период ~2 с                  |
| `OFPT_PACKET_IN`               | коммутатор → контроллер | пакет без совпадения в таблице потоков (table-miss) |
| `OFPT_PACKET_OUT`              | контроллер → коммутатор | что сделать с конкретным пакетом                    |
| `OFPT_FLOW_MOD`                | контроллер → коммутатор | установка правила в таблицу потоков                 |
