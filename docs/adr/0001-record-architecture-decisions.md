# ADR-0001. Фиксировать архитектурные решения в ADR

- **Статус:** Accepted
- **Дата:** 2026-10-09

## Контекст

Репозиторий вырос из набора отчётов в исполняемый проект: топологии на Python,
обходы дефектов Floodlight, автоматические тесты на реальных Mininet и
Floodlight. Причины многих решений неочевидны из кода (например, отключение
IPv6 или перезапуск контроллера в тестах) и без записи будут утеряны или
отменены как «лишние».

## Решение

Архитектурно значимые решения фиксируются в `docs/adr/` в формате Michael
Nygard: «Контекст / Решение / Последствия», по одному файлу на решение.

- Имя файла: `NNNN-kebab-case-title.md`, нумерация сквозная, номера не
  переиспользуются.
- Статусы: `Proposed`, `Accepted`, `Deprecated`, `Superseded by ADR-NNNN`.
- Принятый ADR не редактируется по существу; изменение решения оформляется
  новым ADR со ссылкой на заменяемый.
- Схемы хранятся как исходники Mermaid (`docs/adr/diagrams/*.mmd`) и
  сгенерированные SVG рядом. Перегенерация – `make diagrams`.
- Индекс ADR и схемы процессов – `docs/adr/README.md` и
  `docs/adr/processes.md`.

ADR описывают «почему». Требования («что должно выполняться») описываются в
спецификациях `openspec/specs/`. ADR и спецификации ссылаются друг на друга.

## Последствия

- Каждое изменение, вводящее обход, ограничение или новую зависимость,
  сопровождается ADR.
- SVG MUST перегенерироваться при изменении `.mmd`; расхождение исходника и
  картинки считается дефектом.
- Для рендера нужен Node.js (mermaid-cli скачивается через `npx`); для чтения
  схем ничего не нужно: GitHub показывает SVG.
